# 진단 보고서 작업 프로세스 기획 — 역할 분담과 시스템 지원

작성: 2026-09-08 · 상태: 기획(제안) · 관련: [데이터-거버넌스.md](데이터-거버넌스.md), [서비스기획서.md](서비스기획서.md)

## 0. 한 줄로

**사람은 판단하고, AI는 채우고, 코드는 계산한다.**
보고서 한 건은 네 사람의 손을 거치며 상태가 다섯 번 바뀐다. 시스템의 일은
그 인계(handoff)를 잃어버리지 않게 하는 것이다.

## 1. 왜 역할을 나누는가

보고서를 한 사람이 처음부터 끝까지 쓰면 두 가지가 동시에 병목이 된다 —
**현장 경험**(무엇을 볼지 아는 것)과 **문서 작업**(형식을 갖추는 것). 둘은 다른 능력이고
같은 사람에게 있을 이유가 없다. 그래서 넷으로 나눈다.

| 역할 | 무엇을 아는 사람인가 | 무엇을 하는가 |
| --- | --- | --- |
| **사무실 작성자** | 보고서 형식과 과거 사례 | 큰 틀을 잡고, 나중에 형식을 맞춘다 |
| **현장 경력자** | 무엇을 봐야 하는지 | 체크리스트로 현장 데이터를 올린다 |
| **AI** | 자료 전체를 빠짐없이 훑는 것 | 시계열을 모으고 디테일을 채운다 |
| **현장 책임자** | 이 보고서가 나가도 되는지 | 검증하고 승인한다 |

## 2. 프로세스 5단계

```
① 골격            ② 현장            ③ 채움          ④ 정리        ⑤ 승인
─────────        ─────────         ─────────      ─────────    ─────────
사무실 작성자      현장 경력자         AI              사무실 작성자   현장 책임자
 + LLM

기존보고서·위키    체크리스트로       시계열 분석 +    포맷 정리      검증·승인
→ 보고서 큰 틀     진단·작업 데이터   디테일 문장화                   → 확정
                   서버 업로드

  skeleton    →     measured     →    drafted    →   formatted  →  approved
```

**핵심 순서: 골격이 체크리스트를 결정한다.**
무엇을 보고서에 쓸지 정해야 현장에서 무엇을 확인할지가 정해진다. 반대로 하면
현장에서 재방문이 생긴다 — 쓰려고 보니 그 값이 없는 상황.

---

### ① 골격 — 사무실 작성자 + LLM

| | |
| --- | --- |
| 입력 | 과거 보고서(RAG 검색), 위키 `facility`·`equipment`·`measure` 페이지 |
| 출력 | **보고서 골격** — 목차, 다룰 설비, 검토할 개선안(ECM) 후보, 필요한 실측 항목 |
| 시스템이 할 일 | 유사 사업장의 과거 보고서를 찾아주고, 그때 쓰인 ECM 을 목록으로 준다 |

여기서 LLM 은 **찾아주는 역할**이다. "이 업종 이 규모 사업장에서 예전에 뭘 다뤘나"를
RAG 로 검색하고 위키에서 재사용 가능한 항목을 끌어온다. 골격 자체는 사람이 정한다 —
무엇을 다루고 무엇을 뺄지는 수주 범위와 고객 사정이 걸린 판단이라 AI 가 알 수 없다.

### ② 현장 — 현장 경력자

| | |
| --- | --- |
| 입력 | ① 의 골격에서 파생된 체크리스트 |
| 출력 | 해당/비해당 판정 + 실측값(용량·온도·공기비·가동시간…) + 현장 사진·메모 |
| 시스템이 할 일 | 인쇄 가능한 한 장, 그리고 **값을 구조화해 받는 입력 화면** |

경력자의 시간은 비싸다. 현장에서 요구할 것은 **판정과 숫자뿐**이어야 하고,
문장을 쓰게 하면 안 된다. 지금 체크리스트는 "적을 칸이 있다"까지만 보장하고
값의 형식이 자유다 — 여기를 구조화하는 것이 이 기획의 첫 번째 실행 항목이다(§6).

### ③ 채움 — AI

| | |
| --- | --- |
| 입력 | ② 의 실측값 + 위키 자산(`measure`·`metric`·`regulation`) + ① 의 골격 |
| 출력 | 골격의 각 절에 들어갈 **본문 초안** + 시계열 분석 |
| 시스템이 할 일 | 시계열 집계, 산식 계산(코드), 문장화(LLM), 근거 인용 |

AI 가 가장 잘하는 자리다 — 사람이 놓치는 것을 빠짐없이 훑는 일. 두 가지를 한다.

**시계열 분석**: 같은 사업장·같은 설비가 해가 바뀌며 어떤 값을 보였는지 모은다.
"작년 공기비가 1.3 이었는데 올해 1.5" 같은 변화는 사람이 기억으로 잡기 어렵다.

**디테일 채움**: 골격의 절마다 실측값과 위키 자산을 엮어 본문을 만든다.

### ④ 정리 — 사무실 작성자

| | |
| --- | --- |
| 입력 | ③ 의 초안 |
| 출력 | 제출 형식에 맞춘 보고서 |
| 시스템이 할 일 | 근거를 펼쳐볼 수 있는 편집 화면, docx 내보내기 |

AI 초안은 내용은 맞아도 형식이 어긋난다. 고객사 양식, 절 번호, 표 형식, 문체 —
이건 사람이 맞춘다. 편집 중에 **각 문장의 근거를 즉시 볼 수 있어야** 한다.
근거를 못 보면 고치다가 틀린 문장을 만든다.

### ⑤ 승인 — 현장 책임자

| | |
| --- | --- |
| 입력 | ④ 의 정리본 |
| 출력 | 확정 보고서 + **위키 자산으로 승격** |
| 시스템이 할 일 | 검증 화면(근거·산식 추적), 승인 기록, 승격 처리 |

**승인은 되돌릴 수 없는 지점이다.** 승인 전까지 이 보고서의 내용은 다른 문서가
인용할 수 없고, 승인 후에는 팀의 공식 견해가 되어 다음 진단의 자산이 된다.
데이터 계약의 `doc_status: draft → reviewed` 가 정확히 이 전이다.

## 3. 사람과 AI의 경계

무엇을 AI 에 맡기지 **않을지**를 먼저 못 박아야 한다. 이 경계가 흐려지면
보고서 전체의 신뢰가 한 번에 무너진다.

| | 누가 | 왜 |
| --- | --- | --- |
| 자료 검색·요약 | **AI** | 사람보다 빠짐없이 훑는다 |
| 시계열 집계 | **AI** | 사람의 기억으로는 안 잡힌다 |
| 문장 작성 | **AI** | 초안 수준이면 충분하다 |
| **계산** | **코드** | 같은 입력에 같은 숫자가 나와야 한다 |
| **해당/비해당 판정** | **현장 경력자** | 눈으로 봐야 안다 |
| **다룰 범위 결정** | **사무실 작성자** | 수주 범위·고객 사정이 걸린다 |
| **승인** | **현장 책임자** | 책임이 따른다 |

### 계산을 LLM 에 맡기지 않는 이유

절감량·회수기간은 `llmwiki/ediag/calc.py` 가 계산한다. LLM 은 그 결과를 문장으로 옮길 뿐이다.
LLM 이 계산하면 같은 입력에 다른 숫자가 나올 수 있고, 그러면 검산이 불가능하다.
보고서에 들어가는 숫자는 **`측정값 → 산식 → 결과`** 가 항상 따라다녀야 한다.

### 지어내지 않기

`audit.py` 가 이미 지키는 원칙이다 — *"아이템 후보는 지어내지 않는다.
위키에 measure 페이지가 없으면 설비 골격만 돌려주고 비어 있음을 그대로 말한다."*
③ 의 디테일 채움에도 그대로 적용한다. 실측값이 없으면 `[미측정]` 으로 두고 넘어간다.
빈칸은 사람이 채울 수 있지만, 그럴듯한 거짓값은 아무도 못 잡아낸다.

## 4. RAG 와 LLM Wiki 는 어디에 쓰이나

| | **RAG** (rag.ets0404.com) | **LLM Wiki** (work.ets0404.com) |
| --- | --- | --- |
| 한 문장 | 모르는 자료를 **파악**한다 | 파악한 것을 **자산**으로 쌓는다 |
| 쓰이는 단계 | ① 골격 (과거 보고서 검색) | ①③⑤ (자산 제공·근거·승격 대상) |
| 단위 | 청크(문단) | 페이지(개념) |
| 질문 형태 | "이 보고서에 뭐라 쓰여 있지?" | "우리가 아는 보일러 개선안이 뭐지?" |
| 수명 | 그 건이 끝나면 끝 | 다음 진단에서 다시 쓰인다 |

경계는 기능이 아니라 **자료의 상태**로 긋는다 — 아직 이해 중인가, 이미 이해해서
재사용할 것인가. 원본은 RAG 에만 두고 위키는 `stable_id` 로 참조만 한다(사본 금지).

### 위키 페이지 8종과 현황 (2026-09-08 서버 실측, 70건)

`diagnosis` 8 · `facility` 8 · `equipment` 22 · `measure`(ECM) 7 · `metric` 12 ·
`regulation` 3 · `concept` 2 · `source` 8 — 상태 `reviewed` 49 / `draft` 21.

**`measure` 가 7건뿐**인 것이 지금의 병목이다. ① 골격과 ② 체크리스트가 모두 이
페이지에서 항목을 뽑으므로, 자산이 쌓이기 전까지 두 단계 모두 골격만 나온다.
⑤ 승인이 자산을 늘리는 유일한 경로이므로 — **사이클을 한 바퀴 돌리는 것 자체가 급하다.**

## 5. 인계물과 상태

각 단계의 산출물이 다음 단계의 입력이다. 상태로 표현하면 지금 누구 손에 있는지가 분명해진다.

| 상태 | 뜻 | 다음 행동을 할 사람 |
| --- | --- | --- |
| `skeleton` | 골격이 잡혔고 현장 나가기 전 | 현장 경력자 |
| `measured` | 현장 데이터가 올라옴 | AI (자동 착수) |
| `drafted` | AI 초안 완료 | 사무실 작성자 |
| `formatted` | 형식 정리 완료, 검토 대기 | 현장 책임자 |
| `approved` | 확정 — 위키 자산으로 승격 | (완료) |

되돌리기는 허용하되 **기록을 남긴다**. `formatted → measured` 처럼 뒤로 갈 수 있어야
현장 재방문이 반영된다. 다만 왜 되돌렸는지가 남아야 다음에 같은 실수를 막는다.

### 권한

역할이 곧 권한이다. 현재 데이터 계약에는 열람 등급(ACL 4단계)만 있고 **역할 개념이 없다.**
⑤ 승인을 아무나 못 하게 하려면 역할 필드가 필요하다.

| 역할 | 할 수 있는 상태 전이 |
| --- | --- |
| 사무실 작성자 | `skeleton` 생성, `drafted → formatted` |
| 현장 경력자 | `skeleton → measured` |
| 현장 책임자 | `formatted → approved`, 되돌리기 |

## 6. 구현 현황과 격차

| 단계 | 있는 것 | 없는 것 |
| --- | --- | --- |
| ① 골격 | RAG 하이브리드 검색·대화, 위키 페이지 조회 | **보고서 골격이라는 개념 자체** (지금은 사람 머릿속) |
| ② 현장 | 체크리스트 생성·저장, 인쇄 | **구조화된 실측값 입력** (지금은 자유 형식) |
| ③ 채움 | `calc.py` 산식, 위키 자산 조회 | **본문 초안 생성**, **설비별 시계열** |
| ④ 정리 | — | 편집 화면, 근거 펼쳐보기, docx 내보내기 |
| ⑤ 승인 | `doc_status` 필드 | 검증 화면, 승인 기록, 역할 권한 |

### ⚠️ 시계열이 이름만 있다

`/api/audit/timeseries` 는 문서 주석에 *"같은 설비가 해가 바뀌며 어떤 값을 보였는지 모은다"*
라고 적혀 있지만, 실제 구현은 **위키 페이지 개수를 연도별로 세고 있다**(자산 재고 현황).
③ 이 필요로 하는 *설비 실측값의 연도별 추이*는 아직 없다. 이름이 같아서 있다고 착각하기 쉽다.

실측값 시계열이 성립하려면 ② 의 구조화 입력이 선행돼야 한다 — 값이 자유 형식이면
연도 간 비교가 불가능하다.

## 7. 다음 단계

| 순서 | 할 일 | 왜 이 순서인가 |
| --- | --- | --- |
| **1** | 체크리스트 **실측값 스키마 확정** (설비별 필드·단위·형식) | 이게 없으면 ③ 이 계산할 입력도, 시계열로 비교할 축도 없다 |
| **2** | 보고서 **상태 모델**과 역할 권한 (`skeleton`~`approved`) | 인계가 정의돼야 화면을 어디에 붙일지 정해진다 |
| 3 | 설비별 실측값 **시계열** (진짜 구현) | 1번 위에서만 성립 |
| 4 | ③ **본문 초안 생성** — 골격 배열 + 근거 인용 + 빈칸 표시 | 1·3 이 입력 |
| 5 | ④ 편집 화면 + docx 내보내기 | |
| 6 | ⑤ 검증·승인 화면 + 위키 승격 | 사이클이 닫힌다 |

**1번이 먼저다.** 실측값이 구조화되지 않으면 3·4가 모두 성립하지 않는다.

한편 **사이클을 한 바퀴 돌리는 것**이 기능 완성도보다 급하다. `measure` 7건으로는
① 과 ② 가 계속 빈약하고, 자산은 ⑤ 를 지나야만 늘어난다. 4·5·6 이 거칠더라도
한 건을 끝까지 통과시켜 보는 편이 낫다.

## 8. 미해결 질문

- 골격 단계에서 **현장 재방문을 줄이려면** 무엇을 미리 물어야 하는가? (체크리스트 항목의 완성도)
- 체크리스트 한 장 = 보고서 하나인가, 사업장 하나에 여러 장을 묶는가?
- 과거 보고서를 **문체 참고**로 쓸 것인가? (쓴다면 RAG 검색 결과를 few-shot 으로)
- 승인된 보고서를 위키 `diagnosis` 페이지로 **자동 승격**할 것인가, 사람이 고를 것인가?
- 현장 사진·메모는 어디에 두는가? (RAG 원본 보관소 vs 위키 `source` 페이지)
