접점은 셋이고, 점수제는 남는다

정리된 RFP 원문이 회의 녹취보다 정확하다. 원문을 절 단위로 훑으니 지난번 판단 세 가지가 틀렸다 — 그중 둘은 우리에게 유리한 쪽으로 틀렸다.

지난번 판단에서 고칠 것

녹취는 말한 사람의 요약이고 RFP는 발주 문서다. 둘이 다르면 RFP가 이긴다. 아래 넷은 지난 갭 문서에서 잘못 잡았던 지점이다.

접점은 2개가 아니라 3개

SR 식별 · 이행 게이트 → SR 식별 · IT 접수 · PMO 종료

미승인이면 IT 접수 자체가 불가하고, 검증 결과가 미승인이면 PMO 종료가 불가하다. 게이트가 두 군데로 갈려 있고 막는 대상도 다르다.

Phase 1 나.A · 나.B · 나.C

점수제를 버리라던 권고는 거둔다

Yes / No 로 전환 → 위험점수 · 잔여위험비율 유지

RFP는 “항목별 위험점수 관리”와 “평가항목별 위험경감대책, 잔여위험비율 관리”를 명시한다. 지금 우리 32항목 배점과 완화 가중치가 오히려 이 문구에 정확히 맞는다.

Phase 1 가.C.i · 가.C.ii

“자동화”는 LLM 평가가 아니다

프롬프트 배치로 실측 → 체크리스트 → 사전 맵핑

RFP가 말하는 자동화는 체크리스트로 AI 유형을 식별하면 위험항목이 연동돼 자동 식별되고, 항목마다 경감방안이 사전 맵핑되어 자동 도출되며, 경감비율이 100%로 사전 적용되는 것이다. 전부 수기 수정 가능이 조건으로 붙는다. LLM 실측은 Phase 2 “자동화 가능한 항목의 평가방안 제시”에 해당한다.

Phase 1 가.E · Phase 2 차.A

전자결재는 미정이 아니라 연동

붙일지 미정 → 조회 · 증적 연계 · 위원회 승인

사전검토의뢰서·결과서를 전자결재시스템에서 조회해 프로젝트의 위험경감이행 증적으로 잇고, 윤리위원회 회차별 의결도 전자결재와 연동한다. 그리고 통합인증·보안 SW는 발주처가 이미 쓰는 제품으로 구성해야 한다 — 우리가 고르는 게 아니다.

Phase 1 다 · 마.D · 아.A

세 개의 게이트

이 시스템은 조회용이 아니라 차단기다. 승인이 없으면 IT 접수가 막히고 PMO가 닫히지 않는다. 가용성과 응답 지연이 곧 IT 프로세스 전체의 지연이 된다는 뜻이다.

RFP 문구에 이미 답이 있는 것

제안서에서 “구현하겠습니다”가 아니라 “이미 이렇게 되어 있습니다”로 쓸 수 있는 항목들이다. 왼쪽이 우리 자산, 오른쪽이 그 자산이 답하는 RFP 문구다.

  • append-only 저널라.A~C · 라.E · 바.B 삭제가 없고 대체만 있다. 제개정 이력, 특정 시점 담당자 추적, 작성·수정·승인·반려 이력, “승인 문서 수정 불가”가 전부 하나의 자료구조에서 나온다.
  • 조문 → 의무 → 통제 → 증적 그래프카.A · 라.A “근거 법규 매핑”을 관계로 갖는다. 지표 하나를 눌렀을 때 어느 조문에서 왔는지가 링크로 나온다.
  • 원문 스팬 대조카.A · 차.A 인용문을 원문에서 다시 찾아 오프셋을 기계가 맞춘다. 지어낸 근거는 제안 단계에서 버려진다.
  • 32항목 배점 · 잔여위험비율가.C.i · 가.C.ii · 가.E 위험점수와 경감 후 잔여비율이 이미 같은 계산식 안에 있다. 마스터 파일이 단일 원본이라 항목을 바꾸면 화면과 계산이 함께 따라온다.
  • 룰 판정 · 유보 큐차.A · 차.B 판정 경로에 LLM이 없어 같은 입력이면 같은 답이 나오고, 애매하면 사람에게 넘긴다. 자동평가 가능/불가를 가르는 기준이 이미 코드로 서 있다.
  • 제안 / 판정 / 확정 3분할바.A · 가.E 모델은 제안만, 룰이 판정, 사람이 확정. “자동 도출하되 수기 수정 가능”과 “승인요청자와 승인자 분리”가 같은 원칙의 두 얼굴이다.

RFP 안의 비용 · 일정 함정

견적을 내기 전에 값을 매겨야 하는 조항들이다.

  • 아.C운영에 필요한 SW 추가 시 비용은 제안사 부담. 품질 관리나 테크 진단 솔루션을 얹는 순간 그 라이선스가 우리 원가가 된다. 부가 제안으로 언급하되 기본 범위와 비용에는 넣지 않는다.
  • 아.A통합인증·보안 SW는 발주처 운영 제품으로 구성. 제품 선택권이 없으므로 연동 공수를 먼저 확인해야 한다. 목록을 받아야 견적이 확정된다.
  • 나.B · 나.C미승인 시 IT 접수 불가 · PMO 종료 불가. 이 시스템이 멈추면 IT 프로세스가 멈춘다. 가용성 요건과 장애 시 우회 절차를 제안서에 먼저 써 두는 편이 안전하다.
  • 가.D산출물 15종. 서식 확정이 늦어지면 개발이 통째로 밀린다. 착수 첫 달에 서식부터 잠그는 일정으로 잡아야 한다.
  • 라.E산출물과 감사 로그의 법정 보관기간 관리. 보관 연한·아카이빙·삭제 정책이 스토리지 규모와 백업 설계를 좌우한다.
  • 바.G제3자 검증기관의 임시 시스템 접근. 외부 인력 계정을 기간 한정으로 열고 검증 결과를 등록하게 해야 한다. 보안 심사가 따라붙는 항목이다.

다음 동작

RFP가 정리됐으므로 목업과 견적의 기준선도 이 문서로 바뀐다.

  • 우리목업 수정 — 접점 3개로 고치고, 위험평가를 점수·잔여위험비율 방식으로 되돌린다. 체크리스트 → 자동 식별 → 경감방안 자동 도출 화면을 넣는다.
  • 우리산출물 15종 서식 목록 — 각 문서의 항목과 자동 채움 가능 범위를 표로 만든다. 착수 후 첫 병목이 여기다.
  • 우리 → 고객가견적 — Phase 1 / Phase 2 분리. 추가 SW는 제안사 부담이므로 기본 범위에서 뺀다.
  • 고객 → 우리연동 대상 목록 — 통합인증·보안 제품, 전자결재 API, 알림 API, 인사 테이블. 이게 있어야 견적이 확정된다.
  • 우리자동화 가능 항목표 — Phase 2 차.A가 요구하는 “항목별 평가방안”. AI-RMF 항목마다 자동/반자동/수기를 갈라 제안서에 넣는다.
