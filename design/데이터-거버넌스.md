# 데이터 거버넌스 — 문서 레지스트리 설계와 P1 구현 (v1.0)

작성: 2026-08-27 · 상태: **P1 구현·배포 완료** · 대상: rag.ets0404.com / work.ets0404.com(LLM Wiki) / ets0404.com

## 1. 배경

세 서비스가 같은 서버(Work+Web, 211.119.38.216)에 있으면서 각자 파일을 따로 받는다.
**RAG 서비스를 문서 레지스트리(원본 보관소 + 메타데이터 대장)로 승격**하고,
다른 서비스는 파일을 복사해 가는 대신 stable ID로 참조해 작업한다.

전제가 하나 빠져 있었다 — 기존 RAG는 **원본 파일을 저장하지 않았다**.
업로드하면 텍스트만 추출해 청크·임베딩으로 Qdrant에 넣고 원본을 버렸다.
원본이 없으면 파서를 교체해도 재인제스트할 수 없고, 인용 근거를 사람이 확인할 수 없으며,
해시 검증이 불가능하다. P1은 이 전제를 세우는 작업이다.

## 2. 데이터 계약 (Data Contract) 6축

폼(form)을 먼저 정해 놓으면 그 뒤로는 규격이 있으니 서로 합의된 언어로 얘기할 수 있다.
에이전트도 마찬가지다 — 받는 형식이 매번 다르면 같은 질문에 다른 결과가 나온다.

| 축 | 형식 | 목적 |
| --- | --- | --- |
| stable ID | `doc:ets:<slug>-<연도>-<일련>` 예: `doc:ets:audit-2026-031` | 제목·경로가 바뀌어도 불변인 참조 키 |
| version + hash | 정수 version + 원본 sha256 (인용 시 앞 12자리) | 어느 시점을 인용했는지 고정, 변조 감지 |
| source span | `section_no` + `start_line`/`end_line` | 문서가 아니라 **문단**을 인용 |
| ACL | `PUBLIC / INTERNAL / CONFIDENTIAL / RESTRICTED` | 권한 밖 문서는 검색·목록·다운로드에서 배제 |
| provenance | 원문 경로 · 파서 · 파서 버전 · 변환 일시 | 이 문서가 어떻게 만들어졌는가 |
| owner · status | 담당 조직 + `draft / reviewed / deprecated` | 책임 조직과 신뢰 상태 |

**stable ID에 시각을 넣지 않는 이유**: 초 단위까지 넣으면 갱신할 때마다 ID가 바뀌어
"같은 문서가 업데이트됐다"는 사실을 추적할 수 없다. ID는 고정하고 version이 시간축을 맡는다.

### 인용 표기 (전 서비스 공통)

```
[doc:ets:audit-2026-031 v3 #a1b2c3d4e5f6 s02:14-29]
 stable_id            version  sha256 앞 12자리  섹션:줄범위
```

버전과 해시가 함께 있어야 나중에 "그때 그 문서"를 정확히 재현할 수 있다.

## 3. P1 구현 (완료)

### 스키마

`Document` 한 행 = 하나의 `(stable_id, version)`. 갱신은 **append-only** —
이전 버전 행과 원본 파일을 남긴다. 과거 답변이 인용한 근거를 재현할 수 있어야 하기 때문이다.

```python
stable_id, version, sha256, acl, owner, doc_status,
provenance(JSON), file_path, mime, size_bytes, chunk_count
```

`User`에는 `acl`(열람 최대 등급, 신규 가입자 기본 `PUBLIC`)과 `is_service`(서비스 계정)를 추가했다.

### 원본 보관

```
/opt/rag/data/files/{stable_id의 콜론을 __로 바꾼 값}/v{version}/{원본파일명}
예: /opt/rag/data/files/doc__ets__audit-2026-031/v3/보고서.pdf
```

업로드 시 sha256을 계산해 대장에 기록하고, 다운로드 시 다시 계산해 대조한다.
불일치하면 409를 반환한다 — 조용히 내려주면 변조를 못 잡는다.

### API

| 메서드 | 경로 | 용도 |
| --- | --- | --- |
| POST | `/collections/{id}/upload` | 업로드. `stable_id` 없으면 신규 발급, 있으면 새 버전 |
| GET | `/registry` | 문서 목록 (`status`, `collection_id`, `latest_only`) |
| GET | `/registry/{stable_id}` | 메타데이터. `?version=N` 으로 시점 고정 |
| GET | `/registry/{stable_id}/versions` | 버전 이력 |
| GET | `/registry/{stable_id}/file` | 원본 다운로드 (ACL 검사 + 해시 대조) |
| PATCH | `/registry/{stable_id}` | 거버넌스 필드만 수정 (doc_status·acl·owner) |

**경로가 `/docs`가 아니라 `/registry`인 이유**: `/docs`는 FastAPI가 Swagger UI로 이미 쓴다.

동작 규칙
- 같은 내용을 다시 올리면 `status: unchanged` — 버전을 올리지 않는다.
  version은 "내용이 달라졌다"는 신호여야 한다.
- 새 버전의 `doc_status`는 `draft`로 시작한다. 아직 검토되지 않았기 때문이다.
- 내용 변경은 반드시 새 버전으로. PATCH는 거버넌스 필드만 건드린다.
- 업로더가 자기 등급보다 높은 문서를 만들려 하면 403 — 스스로 못 읽는 문서가 생기는 것을 막는다.

### 섹션 인지 청킹

이미 구조가 있는 문서를 문자 수로만 자르면 문장·표가 중간에서 끊긴다.
헤딩으로 먼저 섹션을 나누고, 섹션이 `CHUNK_SIZE`를 넘을 때만 그 안에서 기계적으로 쪼갠다.

인식하는 헤딩: 마크다운 `#`~`######` · 번호 항목 `2.` `2.1` · 법령 조문 `제3조(적용범위)` · `[Page N]`
(`2024. 6. 30` 같은 날짜가 헤딩으로 오탐되지 않도록 제목 쪽 첫 글자를 확인한다.)

의미 기반(semantic) 청킹은 채택하지 않았다 — 문서가 늘수록 비용이 급격히 커지는 데 비해,
어차피 임베딩·리랭킹 단계에서 상당 부분 흡수된다. 전처리를 잘 해두고 기계적으로 자르는 편이 낫다.

각 청크는 `section_no`, `section_title`, `start_line`, `end_line`을 payload에 싣는다 — 이것이 source span이다.

### 청크 ID

```
청크 키:  doc:ets:audit-2026-031@v3#0007      (사람이 읽는 용도)
point id: 위 키에서 uuid5로 파생 (결정적)
```

결정적이므로 같은 버전을 다시 인제스트해도 청크가 중복되지 않고 덮어써진다.

### 하이브리드 검색 (BM25 + 벡터, RRF)

한쪽만 쓰면 각각의 약점이 그대로 드러난다.
BM25는 `MB-300`, `로트번호 A17` 같은 **정확한 표기**에 강하고 의미 확장은 못 한다.
밀집 벡터는 정반대다. 그래서 각각 랭킹한 뒤 **RRF**로 섞는다 — 순위만 쓰므로 점수 스케일을 맞출 필요가 없다.

- 스파스: fastembed `Qdrant/bm25` + Qdrant `Modifier.IDF`
- 신규 컬렉션은 명명 벡터 `dense` + 스파스 `bm25` 스키마로 생성
- **구 컬렉션(무명 밀집 벡터 하나)은 자동으로 밀집 전용 검색으로 폴백** — 스키마 변경은 재색인이 필요하므로 건드리지 않는다
- 응답의 `retrieval` 필드가 `hybrid_rrf` / `dense` 중 무엇이 쓰였는지 알려준다

### ACL 게이트

- 검색은 Qdrant 필터 단계에서 등급을 건다 — "찾았지만 못 보여준다"는 존재 자체를 노출하므로 아예 제외한다
- 목록·메타 조회·다운로드는 권한이 없으면 403이 아니라 **404**를 반환한다
- `acl` 키가 없는 계약 이전 청크는 `INTERNAL` 취급 (PUBLIC 사용자에게 안 보임)
- `RESTRICTED`는 **Qdrant에 넣지 않는다** — 임베딩도 유출면이다. 원본만 보관하고 상태는 `stored_not_indexed`
- **응답 캐시 키에 열람 등급을 포함**한다. 빠뜨리면 상위 등급 사용자의 답변이 하위 등급 사용자에게 재사용된다

### 무결성 린트

만든 직후 한 번 확인해 두는 비용이, 나중에 데이터부터 다시 만드는 비용보다 훨씬 싸다.
데이터 단에서 어긋난 것을 두면 그 위에 쌓는 인덱스·지식그래프·답변이 전부 같이 틀어진다.

```bash
cd /opt/rag/app && /opt/rag/.venv/bin/python lint_contract.py
```

| 코드 | 검사 |
| --- | --- |
| C1 | stable_id 형식 |
| C2 | (stable_id, version) 중복 |
| C3 | 보관 원본 존재 |
| C4 | 원본 해시 = 대장 해시 (변조·교체 감지) |
| C5 | ACL / doc_status 허용값 |
| C6 | provenance JSON 파싱 |
| C7 | processed 인데 청크 0개 |
| C8 | Qdrant 청크 payload = 대장 (`--fix-payload` 로 정정 가능) |
| C9 | 대장에 없는 고아 청크 |
| C10 | 청크에 span 정보 존재 |

정기 실행(cron)을 권장한다. LLM이 만든 데이터는 같은 입력에도 결과가 흔들릴 수 있어,
"만들었으니 맞겠지"를 전제로 두면 안 된다.

## 4. 검증 결과 (2026-08-27, 서버 실측)

전 항목 통과. 확인한 것:

- stable_id 자동 발급, 업로드 해시 = 로컬 해시
- 원본 보관 및 **바이트 단위 일치** 다운로드, 해시 헤더 일치
- provenance 기록(파서·변환일시·업로더), owner·doc_status 보존
- 하이브리드 검색이 두 질의 유형 모두 `hybrid_rrf` 경로, 계약 인용 표기와 span 포함
- 같은 내용 재업로드 → `unchanged` (버전 안 올라감)
- 내용 변경 → v2 생성, **v1 원본과 해시가 그대로 보존**되어 과거 시점 재현 가능
- ACL: 신규 가입자 PUBLIC / INTERNAL 문서가 목록·메타·다운로드·검색 모두에서 차단
- 린트 위반 0건

## 6. 운영 수칙

- `deprecated` 문서는 검색 기본값에서 제외하되 **삭제하지 않는다** (인용 재현 보장)
- `/opt/rag/data/files/`와 `rag.db`는 **같은 백업 단위**로 묶는다 (대장과 원본의 정합)
- 파서 교체 시 provenance의 파서 이름·버전으로 재인제스트 대상을 식별한다
- 소비 서비스는 파일을 복사해 가지 말고 stable_id로 참조하고, 캐시는 `sha256`이 같을 때만 재사용한다
- LLM Wiki는 앱 자체 인증이 없으므로 레지스트리 호출은 **백엔드에서만** 하고 토큰을 브라우저에 내리지 않는다
