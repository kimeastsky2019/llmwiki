## 1. 문제

### 1.1 SI 산출물은 제출한 다음 날부터 낡는다

프로젝트 종료 시점에 프로그램 명세서를 제출합니다. 그리고 **일주일이면 쓰레기가 됩니다.**
소스는 SM 단계에서 계속 바뀌는데 산출물을 최신화하는 사람이 없기 때문입니다.
아무도 갱신하지 않는다는 걸 모두 알기 때문에, 시간이 지나면 아무도 열어보지 않습니다.

그 결과 이런 비용이 반복해서 발생합니다.

| 상황 | 실제로 일어나는 일 |
|---|---|
| SM 담당자가 장애 대응 | 문서 대신 소스를 처음부터 읽음 |
| 신규 인력 투입 | 선임 개발자 시간을 뺏어 구두로 인수인계 |
| 차세대/고도화 사업 착수 | As-Is 분석에 수개월과 별도 비용 |
| 테이블 스키마 변경 검토 | 영향받는 프로그램을 grep 으로 찾음. 누락 위험 상시 |
| 패키지 도입 / 인수 시스템 | 내부 구조를 아는 사람이 아예 없음 |

### 1.2 왜 지금까지 해결이 안 됐나

- **사람이 쓰는 방식**: 최신화 담당자가 없다. 조직 문제라 도구로 안 풀림
- **기존 문서화 도구(Javadoc, Doxygen)**: 코드 주석을 뽑을 뿐, *업무* 를 설명하지 않음.
  "이 화면이 무슨 일을 하는가"는 안 나옴
- **LLM 에 소스를 통째로 넣기**: 컨텍스트 한계, 비용, 그리고 **환각**.
  틀린 문서는 없는 문서보다 나쁩니다

## 2. 해결 방식

### 2.1 핵심 아이디어 — 산출물을 배포 파이프라인에 넣는다

```
개발 → 소스 취약점 점검 → [ LLMWiki 산출물 생성 ] → 운영계 반영
                                    ↑
                    운영계에 나가는 소스 = 문서의 근거
```

운영계로 소스를 넘기는 그 시점에 문서를 다시 만듭니다.
**"최신화"라는 별도 작업이 존재하지 않게** 만드는 것이 이 제품의 전부입니다.

### 2.2 차별점 — 사실과 서술을 분리한다

LLM 에 소스를 던져 문서를 받는 도구와 결정적으로 다른 지점입니다.

| 항목 | 생성 주체 | 신뢰 근거 |
|---|---|---|
| 호출 URL, 클래스, 테이블, CRUD 매트릭스, SQL 원문, **호출 흐름도**, **영향도** | **정적 파서** | 소스에서 기계적으로 추출. 추측 없음 |
| 업무 설명, 처리 로직 서술, 파라미터 의미, 오류 처리, 개선 포인트 | **LLM** | 파서가 뽑은 사실만 컨텍스트로 제공 |

흐름도는 LLM 이 그리지 않습니다. 실제 호출 그래프에서 렌더링합니다.
LLM 에게는 *"확인되지 않으면 '소스상 확인 불가'라고 쓰라"* 고 지시합니다.

이 분리는 문장이 아니라 [온톨로지 스키마](온톨로지-스키마.md)에 박혀 있습니다.
모든 사실에 `derivation: static | derived | llm` 이 붙고, 샘플 기준
**노드 146개 중 144개가 `static`** 입니다. 감리에서 "어디까지 믿을 수 있나"를 물으면
`llm` 부분만 검토 대상이라고 답할 수 있습니다.

### 2.3 망분리 대응

금융·공공 소스는 클라우드 API 로 나갈 수 없습니다.
`config.yaml` 의 `provider` 한 줄로 전환합니다.

| provider | 용도 |
|---|---|
| `claude` | 개발·데모·제안 (샘플 소스만) |
| `ollama` | **고객사 사내 GPU 서버** — 실제 반입 |
| `template` | LLM 없이 구조만. 무키 스모크 테스트 |

구문 강조도 외부 라이브러리 없이 직접 구현했습니다. 반입 심사 대상 의존성을 줄이려는
의도적 선택입니다.

### 3.1 구매 결정자와 실사용자

| 역할 | 관심사 | LLMWiki 가 주는 것 |

| **CIO / 정보화본부장** (구매) | 시스템 이해도 상실 리스크, 차세대 사업 준비 | 항상 최신인 시스템 지식 자산 |

| **신규 투입 인력** | 시스템 파악 | 한글 업무명으로 검색 → 소스까지 한 화면 |
| **PMO / 감리** | 산출물 품질·최신성 | 소스 해시 기반 최신성 증명, Excel 제출 |
| **차세대 분석가** | As-Is 파악 | 분석 기간 단축 |

| 지표 | 현재 | 목표 |
|---|---|---|

| 신규 인력 시스템 파악 | 2~4주 | 1주 이내 |

### 4.3 2차 — 설계 사이클 (온톨로지 v1.1)

녹취록에서 논의된 다음 단계입니다.

**문제**: 분석(As-Is)은 *소스* 라는 명확한 입력이 있습니다.
설계(To-Be)는 입력이 *요구사항* 뿐이라 사람마다 품질 편차가 큽니다.
프롬프트를 잘 쓰는 사람과 아닌 사람의 결과물이 완전히 다릅니다.

**해법**: 프롬프트를 자유 서술로 받지 않습니다. **입력 폼(항목별 엑셀)** 으로 받아
평준화한 뒤 프롬프트로 변환합니다. 사람이 프롬프트를 쓰는 게 아니라, 폼을 채우면
시스템이 프롬프트를 만듭니다.

```
요구사항 입력 폼 ─┐
화면 구성도      ─┼─▶ 프롬프트 자동 생성 ─▶ 설계 산출물 ─▶ 소스 생성 ─▶ 테스트
ERD / 테이블 내역 ─┘                            │
                                        테스트 케이스 자동 도출 ─┘
```

온톨로지에 `Requirement` `ScreenSpec` `TestCase` `realizes` `verifies` 를
**이미 예약해 두었습니다.** 요구사항 하나를 클릭하면 그것을 구현한 프로그램,
그 프로그램이 건드리는 테이블, 그것을 검증하는 테스트 케이스가 전부 따라옵니다.
현재 v1.0 은 이 사이클의 **왼쪽 절반**입니다.

## 5. 사업 모델

### 5.1 진입 경로

```
제안/시연 (샘플 소스) → PoC (고객 소스 일부, 사내망) → 1차 사업 → SM 계약에 포함
```

시연에서 CIO 반응이 좋았던 지점: **"산출물이 항상 최신"** 과 **영향도 분석** 두 가지였습니다.
"AI가 문서를 써준다"가 아니라 **"관리 안 해도 안 낡는다"** 로 소구해야 합니다.

### 5.2 과금 후보

| 모델 | 설명 | 적합 |
|---|---|---|
| 구축형 (온프레) | 사내 설치 + 연 유지보수 | 금융·공공 주력 |
| 사업 옵션 | 차세대/고도화 사업에 산출물 자동화 항목으로 포함 | 진입 장벽 최저 |
| SM 계약 포함 | SM 단가에 지식 관리 항목 | 안정 매출 |

### 5.3 원가 구조

증분 생성이라 **바뀐 프로그램만** LLM 을 호출합니다.
1,000본 시스템에서도 일상 배포는 몇 건 수준입니다. 초기 전량 생성이 비용 대부분이고,
그 뒤는 배포 빈도에 비례합니다. 사내 Ollama 사용 시 토큰 비용은 0 이고 GPU 상각만 남습니다.

## 6. 리스크

| 리스크 | 영향 | 대응 |
|---|---|---|
| **정규식 파서의 커버리지** | 특이 코드 누락 | 검증기 + 회귀 테스트. 실패 케이스를 테스트로 추가하며 확장. 온톨로지 위반은 CI 에서 잡힘 |
| **LLM 서술 오류** | 잘못된 문서 신뢰 | `derivation` 으로 구분. 구조는 파서가 담당해 환각 영향 범위를 서술로 한정 |
| **사내 LLM 품질** | 서술 품질 저하 | provider 추상화로 모델 교체 자유. 품질 미달 시 `template` 로 구조만 제공 |
| **소스 반출 규정** | 도입 자체 불가 | 처음부터 온프레 전제. 외부 의존성 최소화 |
| **저작권 / 산출물 귀속** | 분쟁 | 프로젝트 투입 산출물은 통상 고객 귀속. **제품 코드와 프로젝트 산출물을 분리**하고 계약서에 명시할 것 |
| **"AI가 만든 문서" 거부감** | 감리 반려 | `static` 부분은 소스가 근거임을 스키마로 증명. 검토 대상을 `llm` 절로 한정 |

> 저작권 항목은 기술이 아니라 **계약** 이슈입니다. 1차 사업 계약 전에 반드시
> 제품(LLMWiki 코드)과 프로젝트 산출물(생성된 명세서)의 귀속을 나눠 명시해야 합니다.

```
            Excel 내보내기, 다국어, 증분 생성
🔧 진행 중  멀티 프로젝트 워크스페이스, 백그라운드 작업(대형 저장소 대응)
⏳ 미검증   실 규모(1,000본+) 성능, 사내 Ollama 산출물 품질, CI/CD 실연동
```

**다음 한 걸음**: 고객사 소스 일부로 사내 Ollama PoC.
검증할 것은 두 가지입니다 — *실 규모에서 파서가 버티는가*, *사내 모델의 서술 품질이
쓸 만한가*. 전자가 실패하면 파서를 고치면 되지만, 후자가 실패하면 `template` 로
구조만 제공하는 축소 제안이 됩니다. 그 경우에도 영향도·CRUD·흐름도는 그대로 유효합니다.
